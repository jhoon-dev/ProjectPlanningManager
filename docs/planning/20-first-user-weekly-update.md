## 사용자와 업무

첫 사용자는 설비·자동화 구축 프로젝트의 PM 겸 공정 담당자다. 작업의 선후관계를 이해하고,
여러 담당자의 실적을 취합해 일정과 인력 배정을 갱신하며 주간회의 자료를 직접 만든다.
작업 50~300개를 첫 실제 파일럿 범위로 제안한다. 이는 제품 성능 한계나 검증된 시장 규모가 아니다.

대표 업무는 “이번 주 실적과 남은 일을 반영하고, 완료일 변화와 자원 충돌을 확인해
다음 주 조정안을 검토한 뒤 회의 자료와 이어 쓸 파일을 남긴다”이다.
설계 → 부품 준비 → 조립 → 현장 설치 → 시운전 사례를 사용한다.
조립 지연과 같은 담당자의 중복 배정을 포함한다. 최초 점검은 작은 합성 사례이며,
실제 업무 파일·참여자를 사용한 과업 성공 검증과 구분한다.

## 검증 경계

핵심 과업은 계정·서버 없는 단일 native 프로젝트에서 완결한다. 처음에는 기간 기반 작업과
일반 인력 배정을 사용한다. 상태일, 보고 실제/잔여, 계획 기간·공수·물리 진척을 혼동하지 않는다.
새 보고와 정정의 원장·기준선 보존, 입력 변경 후 재계산과 오래된 결과 표시를 유지한다.
자원 조정은 수동 배정 변경 또는 평준화 후보 비교로 검토하며 자동 최적해를 약속하지 않는다.

상세 자재 원장·원가/EVM·외부 계산식·다중 프로젝트·협업은 기존 기능을 유지하되
첫 과업 성공의 선행조건으로 만들지 않는다. MSP/P6 가져오기는 별도 진입 경로다.
실제 제품 왕복 호환성은 [별도 검증](../p6-roundtrip.md)이며 native 과업 성공으로 대체하지 않는다.

## 점검과 실제 사용자 검증

첫 단계는 현재 Windows 앱의 전문가 과업 점검이다. 시작 조건·데이터·실행 파일과 소스 버전,
방문한 메뉴/화면·입력/출력·막힘·우회·미실행 단계를 기록한다. 화면에서 확인한 사실과
소스에서만 확인한 사실, 제안 개선안을 구분한다. [이번 점검 결과](21-weekly-update-ux-review.md).

다음 단계에서는 실제 대상 사용자 3명을 첫 탐색 표본으로 제안한다. 같은 안내문과 실제성이 있는
30~50개 작업 사례로 WEEK-03~07을 수행하게 하고, 도움 요청·입력 오류·중단·소요시간과
완료일/지연 근거 설명의 정확성을 기록한다. 표본 수·시간 목표는 합의 전 제안이며,
현재 성공률·속도·제품 우월성 수치로 사용하지 않는다. 이후 실제 50~300개 업무 파일로 확대한다.

UX 개선 후에도 전체 기능의 개발 완료나 외부 제품 동등성을 선언하지 않는다.
우선 판정은 “도움 없이 주간 갱신을 마치고 완료일 변화와 근거를 설명하며 저장 후 재현하는가”다.
